# 文档校验

## 人工检查

- 文档描述的页面、命令、目录、配置、接口和行为在项目中真实存在。
- 当前实现与设计方案状态没有混淆。
- 文档职责清晰，没有多份有效文档维护同一事实。
- 新增文档已加入对应导航，删除或移动后导航和引用同步更新。
- 最后核对日期只出现在完整复核过的文档中。

## 自动检查

优先运行项目已有的 `docs:check`、Markdown lint、链接检查、格式化或统一 `check` 命令。项目没有文档校验且文档规模已经产生维护风险时，再增加最小脚本。

适合自动化的内容：

1. 核心导航或项目约定的必需文档存在。
2. Markdown 相对链接指向真实文件。
3. 文档头部字段存在且日期格式合法。
4. 导航登记的文件存在，重要文档没有遗漏入口。
5. 可机械识别的 API 路径与 HTTP 方法和实现双向一致。
6. 重复登记、孤立文档或明显无效关联路径。

不适合自动生成或自动判定：

- 产品目标、验收边界和业务语义。
- 架构决策是否合理。
- 鉴权、参数和响应描述是否完整准确。
- 方案是否应该实施。

## 校验脚本原则

- 从当前项目的真实目录、文件命名和框架约定出发，不复制其他项目的路径。
- 失败信息包含具体文档、目标和修复方向。
- 保持只读，不在检查过程中自动重写文档。
- 接入项目已有统一质量门禁，不额外创造没人运行的命令。
- 解析规则必须由文档格式约定支撑，例如固定 API 标题格式；不能依赖脆弱的全文猜测。

## 审查输出

按严重程度报告：

- **高**：当前事实错误、关键命令不可执行、接口契约错误或方案冒充已实现。
- **中**：导航断链、重复文档、关联代码失效、重要变化未同步。
- **低**：标题层级、格式一致性、可读性和维护成本问题。

没有明确问题时，说明已检查的范围、未执行的自动校验和剩余人工风险。
