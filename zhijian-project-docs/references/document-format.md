# 文档格式

## 通用头部

一级标题后维护最小元信息：

```markdown
# 文档标题

- 文档状态：当前实现基线 / 当前功能说明 / 开发规范 / 设计方案 / 已废弃
- 适用范围：当前项目，或明确版本/模块
- 最后核对：YYYY-MM-DD
- 维护范围：本文负责描述的内容
- 关联代码：相关目录、配置、脚本或核心文件
```

项目已经统一使用“文档说明”二级标题时可以沿用，但同一项目保持一致。只有完整核对正文后才能更新“最后核对”。

## 内容原则

- 开头说明本文回答什么问题，以及不负责什么。
- 标题按阅读顺序组织；不要用过深层级模拟代码目录。
- 使用表格表达映射、状态和对比，使用 Mermaid 表达关键数据流或时序。
- 示例必须与真实项目一致；无法执行的命令、路径和配置不要写入当前基线。
- 使用相对 Markdown 链接连接项目内文档，避免复制相同正文。
- 文件名不包含日期或版本号；版本和核对日期放在文档头部。

## 产品文档

需求文档至少说明：产品目标、角色、范围、核心规则、明确不做和验收边界。

功能文档至少说明：入口、权限、用户操作、状态、失败反馈和当前限制。按用户行为描述，不按组件文件流水账展开。

## 技术文档

架构文档至少说明：技术边界、目录或模块职责、依赖方向、数据模型、关键流程、持久化、测试与当前约束。

接口文档格式遵循项目现有框架。没有约定时可使用：

```markdown
## /api/example · 接口用途

### GET · 行为说明

- 鉴权：公开 / 用户 / 管理员
- 参数：Query、Path、Body
- 成功响应：关键结构
- 错误：重要状态码与业务语义
```

同一路径的不同 HTTP 方法分别描述，不能共享模糊的参数或响应说明。

## 方案文档

明确标注“设计方案”，说明当前基线、目标、核心决策、未决问题、阶段状态、风险和落地后的同步目标。

方案落地后：

1. 将最终用户行为同步到需求和功能文档。
2. 将最终技术事实同步到架构或专项技术文档。
3. 更新方案阶段状态；没有历史价值时删除方案。
