# 项目文档体系

## 目标

文档体系回答四个问题：项目为什么做、现在能做什么、当前如何实现、开发时必须遵循什么。目录服务于查找和维护，不追求文件数量。

## 推荐结构

```text
docs/
├─ 00-文档导航.md
├─ 01-产品文档/
│  ├─ 01-需求文档.md
│  └─ 02-功能文档.md
├─ 02-技术文档/
│  └─ 01-架构设计文档.md
├─ 03-开发规范/
│  └─ 00-规范导航.md
└─ 04-方案文档/                 # 有真实未实施方案时再创建
```

这是起点，不是固定模板：

- 小项目只建立真实需要的核心文档。
- 功能、接口或规范增多后再拆子目录，并保留 `00-...导航.md`。
- `99-归档/` 仅用于确有历史价值的过期内容；无保留价值的旧文档直接删除。
- 不因插入单个文件批量重排已有编号，避免无意义链接变化。

## 文档职责

| 类型 | 只负责描述 | 不应包含 |
| --- | --- | --- |
| 需求文档 | 产品目标、角色、范围、业务规则、验收边界 | 未确认技术实现、长期路线图 |
| 功能文档 | 当前入口、权限、用户操作和可见行为 | 组件内部实现细节 |
| 技术文档 | 架构、数据模型、接口、认证、部署和关键数据流 | 尚未实施却写成既有能力的方案 |
| 开发规范 | 目录边界、代码约定、质量门禁和协作规则 | 与项目工具不一致的通用口号 |
| 方案文档 | 未实施设计、决策、阶段目标和风险 | 当前功能基线 |

## 状态模型

- **导航索引**：提供分类、入口、阅读顺序和维护规则。
- **当前实现基线**：描述已落地且可从代码验证的事实。
- **当前功能说明**：描述用户现在能使用的行为。
- **开发规范**：约束当前项目的实现与协作。
- **设计方案**：尚未全部实施的方向和决策。
- **已废弃**：不再适用但确有保留价值。

## 导航规则

- 根导航列出目录结构、分类入口、阅读顺序、命名规则和同步矩阵。
- 子目录内容较多时建立局部导航，不让根导航承担所有细节。
- README 链接到文档导航；AGENTS 或工具速查卡只保留关键入口和常用命令。
- 导航中的状态、数量和说明必须随文档增删同步更新。

## 拆分判断

- 主题单一且能顺畅阅读时保留一个文件。
- 内容接近 300～500 行、包含多个独立主题或不同更新频率时，检查是否需要拆分；行数只是信号，不是硬限制。
- 拆分后按职责划分，不按页面片段或代码文件机械拆文档。
