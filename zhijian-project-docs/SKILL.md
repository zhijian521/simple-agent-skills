# 项目文档管理

维护可与代码共同演进、可定位来源、可验证状态的正式项目文档。先读取项目事实，再更新文档；不要根据设想反推不存在的实现。

## 1. 识别任务

1. **初始化**：项目缺少正式文档体系，需要建立最小目录、导航和核心文档。
2. **同步**：代码、功能、接口、架构或工具链已经变化，需要更新受影响文档。
3. **审查**：检查文档是否过期、重复、断链、状态混淆或与代码不一致。
4. **方案管理**：记录尚未落地的设计，或将已实施方案同步回当前基线。

## 2. 读取项目事实

执行前检查：

- 根 `README`、`AGENTS.md` 或同类项目入口
- `package.json`、构建配置、校验脚本和真实目录结构
- 项目约定的正式文档目录（通常是 `docs/`）、导航、相对链接和文档状态
- 与任务相关的源码、接口、数据库、测试和部署文件
- 当前 diff；同步任务只处理实际受影响的文档

优先级：可执行脚本、配置和已提交实现 > 项目专项规范 > 当前基线文档 > 设计方案 > 通用模板。

## 3. 按需读取 reference

- 初始化或重构文档体系：读取 `document-system.md`。
- 创建或编辑文档：读取 `document-format.md`。
- 根据代码变更同步文档：读取 `sync-matrix.md`。
- 审查文档或设计校验脚本：读取 `validation.md`。

复杂任务可以组合读取，但不要加载与任务无关的模板。

## 4. 执行规则

- 项目约定的正式文档目录作为唯一来源，通常是 `docs/`；README 负责入口，AGENTS 负责速查，不复制完整正文。
- 当前需求、功能和架构只记录已经落地且能从代码验证的事实。
- 未实现内容放入设计方案，并明确状态；不能混入“当前实现基线”。
- 代码与文档在同一次变更中保持一致，但内部实现调整不要求机械更新所有文档。
- 新建目录和文档前先确认真实维护需求，不预建空目录、空索引或未来占位文档。
- 更新“最后核对”日期前，必须重新核对整篇文档与当前代码，而不是只改局部段落。
- 实施结果与方案不同时，以实际代码为准，并同步修订方案和当前基线。

## 5. 完成标准

- 文档内容与当前代码、配置和用户行为一致。
- 新文档已进入对应导航，删除或移动文档后没有断链。
- 状态、适用范围、核对日期、维护范围和关联代码清晰。
- 运行项目已有的格式化、链接检查、文档检查或统一质量门禁。
- 没有可用校验命令时执行人工检查，并在交付中说明未自动验证的部分。

最终回复说明同步了哪些文档事实、运行了哪些校验，以及仍需人工确认的内容；不要按文件逐行复述修改过程。
