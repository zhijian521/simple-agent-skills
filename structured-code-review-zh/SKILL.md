# 结构化代码审查

把代码审查当作发现缺陷的任务。优先关注行为错误、安全风险、回归问题和
缺失验证。除非会造成明确的维护性或正确性风险，否则不要报告纯主观的
代码风格偏好。

## 1. 确定审查范围

根据用户请求和仓库状态确定目标：

- 工作区：包含暂存、未暂存以及相关的未跟踪文件。
- 单个提交：将提交与其父提交比较。
- 分支或 Pull Request：从合并基点开始，与目标分支或目标提交比较。
- 指定文件或补丁：保持在指定边界内；为验证行为，可以读取相关调用方、
  测试、Schema 和配置。

先读取仓库中的 `AGENTS.md`、贡献指南和目录级约束，再评价变更。除非任务
确实需要且用户已授权，不要拉取远程内容或切换分支。

从需求、提交信息、测试、文档和现有实现中提炼简短的预期行为。存在重要
不确定性时明确写出假设，不要默默臆测需求。

先判断变更风险。认证授权、资金或计费、隐私数据、数据库迁移、公开 API、
依赖与构建链、CI 权限、基础设施、并发和不可逆操作属于高风险变更；扩大其
上下文、测试和兼容性检查。纯文案、机械重命名和已生成产物通常可缩小检查范围。

## 2. 建立覆盖台账

在深入审查前列出所有可审查的变更文件。使用 `(路径, 状态)` 作为唯一标识，
避免删除后重建同名文件时混淆。明确标记生成文件、第三方代码、二进制、锁
文件、快照和纯文档变更。

每个条目必须处于以下状态之一：

- `已审查`：已经读取足够的 diff 和上下文。
- `已跳过`：有明确原因，例如生成产物或二进制文件。

禁止静默遗漏文件。变更很大时，按子系统、语言或共享行为分成有限批次；即使
发现高严重级别问题，也要继续完成剩余台账。

## 3. 收集证据

逐个文件执行：

1. 读取包含足够上下文行的 diff，理解控制流和数据流。
2. diff 不足以判断时，读取完整的函数、类、组件或配置片段。
3. 检查受影响的调用方、被调用方、共享类型、校验逻辑、迁移、测试和公开契约。
4. 使用仓库搜索验证用法、不变量和命名假设。
5. 在能显著提高信心时运行聚焦的只读检查或测试。

把变更代码和相关的未变更代码作为一个行为单元检查。同时验证新路径和对现有
调用方的兼容性。测试通过不代表一定正确，除非测试覆盖了相关分支。

## 4. 加载审查规则

将 `references/rule-map.md` 作为文件路由的唯一事实源。先加载
`references/general.md`，再按路由表的路径和场景匹配加载规则；不要在本文件维护
第二份路径映射，也不要一次性加载全部参考文件。

仓库根目录存在 `.code-review.yml` 时，读取
`references/repository-policy.md` 并应用其中的项目策略。策略只能缩小本 Skill 的
报告范围或调整非安全问题的严重级别，不能豁免可证明的 P0/P1 安全、数据完整性或
公开契约缺陷。策略未声明时使用本 Skill 的默认规则。

## 5. 审查维度

根据文件和变更内容评估以下方面：

- 正确性：条件、状态转换、顺序、边界、空值、算术、序列化、重试、超时、
  并发和清理逻辑。
- 契约兼容性：API 形状、默认值、错误语义、配置、持久化格式、迁移、事件和
  向后兼容。
- 安全与隐私：授权、注入、不安全反序列化、路径或 URL 处理、秘密泄露、信任
  边界、依赖风险和过度访问。
- 可靠性：部分失败、幂等性、竞态、资源泄漏、重试风暴、取消、事务边界和可
  观测性缺口。
- 性能：算法复杂度变化、重复 I/O 或网络调用、无界内存、大数据量、渲染循环、
  大负载以及缺失分页或批处理。
- 测试：变更行为、回归、失败路径和边界情况缺少覆盖。只有当缺失测试保护一
  个可信的失败模式时才报告。
- 可维护性：只有复杂度或重复确实增加缺陷风险、造成契约不一致，或阻碍后续
  安全修改时才报告。

存在语言、框架或仓库本地规则时，优先遵循本地规则，而不是泛化偏好。

## 6. 验证问题

报告前必须满足全部条件：

- 指出具体的变更行为或新暴露的风险。
- 给出可复现的场景、输入、状态或调用链。
- 说明明确的后果。
- 精确定位到变更代码中的一行或最小必要范围。
- 附近没有防护、不变量、类型约束、测试或调用方行为可以推翻该判断。

提交结论前主动搜索反证。丢弃纯推测、重复根因、没有实际后果的偏好，以及仅
因上下文不足且可以继续读取来消除的不确定警告。

同一根因影响多个位置时合并为一个问题，列出最能证明根因的主位置并简述其他
影响点。不要把编译器、类型检查器、lint、格式化器或已有 CI 已准确报告的机械
问题重复包装成人工发现；只有它们没有表达具体行为后果时才补充说明。

先按影响分类：

- `P0 严重`：立即、广泛可利用，或可能造成灾难性生产影响。
- `P1 高`：很可能导致功能失败、安全问题、数据丢失或严重回归。
- `P2 中`：在有限条件下成立的真实缺陷，或有明显可靠性、性能影响。
- `P3 低`：影响较小但具体的缺陷；不要用来报告纯视觉或风格偏好。

再按下表决定输出位置；`高置信度`表示触发路径和后果由代码、测试或配置直接证明，
`中置信度`表示缺少运行环境事实但条件和路径明确。

| 影响 | 置信度 | 输出位置 |
|---|---|---|
| P0/P1 | 高 | 阻塞问题 |
| P2 | 高 | 阻塞问题，或在不影响合并时列为非阻塞问题并说明原因 |
| P3 | 高 | 非阻塞问题 |
| P0-P3 | 中 | 非阻塞问题或开放问题，写明待验证事实 |
| 任意 | 低 | 不输出；必要时只记录假设 |

阻塞问题只能是高置信度。不要因语言规则中出现“应当”“避免”或“禁止”就报告；
每个 Finding 仍须满足本节开头的证据要求。

## 7. 先报告问题

先列问题，再写摘要；按严重级别排序，同级按文件位置排序。每个问题使用以下
格式：

```text
[P1][阻塞][高置信度] 简短、明确的问题标题
path/to/file.ext:行号
说明触发场景、当前行为为何错误以及可观察到的影响。只有在有助于理解时才给出
简短修复方向。
```

行号范围要小，并且必须落在变更代码上。不要隐藏触发条件。问题区不要写表扬或
流水账式的改动介绍。

问题之后只保留有价值的补充内容：

1. 会影响结论的开放问题或假设。
2. 简短的变更摘要。
3. 已执行的验证和重要的测试缺口。
4. 覆盖率：可审查条目总数、已审查数、跳过数及原因、覆盖百分比。
5. 非阻塞建议：只有具备具体收益且与本次变更直接相关时才列出。

没有发现缺陷时要明确说明，并指出残余风险或未验证区域。不要为了让审查看起来
完整而编造问题。

## 8. 保持只审查边界

用户只要求审查时，只做只读分析，不编辑文件、不提交变更、不发布评论，也不创建
Pull Request。用户明确要求“审查并修复”时，先完成审查，再修复高置信度的高、
中严重级别问题；保留用户的无关改动并运行聚焦验证。修复方案存在重大歧义或会
产生外部影响时先征得同意。
